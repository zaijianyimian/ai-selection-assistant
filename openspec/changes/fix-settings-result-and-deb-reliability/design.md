# Design

## Context

动机与证据见 proposal.md。当前保存流程在凭据操作、快捷键预留和 JSON 落盘之前调用 `Memory::invalidate`；该调用立即提交删除全部 profiles、重置 active/cursor 并递增 epoch。前端的设置 watcher 无条件替换草稿，翻译页从当前全局设置读取语言及术语状态。Job 只有任务 revision，没有请求展示快照。

当前主规格目录为空，已有两个完成但未归档的变更。本变更沿用能力路径，新增独立要求，不修改旧规划文件，也不捎带归档。先前 technical-translation 的单次兼容回退文字与当前实现存在差异，本次不触碰其模型协议要求。

## Goals / Non-Goals

**Goals:** 对可控保存失败提供一致补偿；成功后保持现有 epoch/generation 防旧写入约束；保护草稿；让结果展示跟随实际请求；让成品依赖可验证。

**Non-Goals:** 不引入跨操作系统凭据服务、文件系统、SQLite 的通用分布式事务；不承诺进程被强杀或机器断电时上述多资源完全原子；不保存凭据恢复副本到磁盘；不新增翻译历史或模型能力。不把本机预编译 DEB 扩展为覆盖所有旧发行版的通用包；较低发行版重新构建另列后续变更。

## Decisions

### 1. 分阶段准备与提交，保留数据库事务直至配置发布完成

提取可测试的保存协调逻辑，保留 `state.settings` 锁使多个保存串行，翻译/分析读取设置也经同一锁。显式注入配置文件、凭据、快捷键及记忆提交操作，测试用临时文件和假凭据，不碰真实 Key。

保存顺序：

1. 校验并规范化配置，保存原非敏感配置及必要的内存凭据快照；在目标目录生成待发布配置。任何准备失败都不改变 epoch、generation 或画像。
2. 预留新快捷键；需要时更新凭据。记录已完成操作，以便后续按相反顺序补偿。未变更的资源不做额外读写。
3. 若切换记忆/自动分析选项，在现有数据库 actor 上执行一个短事务：在事务内失效画像，发布已暂存的配置文件，然后提交 SQLite。发布失败则回滚数据库；SQLite 提交失败则回滚数据库并恢复原配置文件，再补偿凭据与快捷键。文件备份只有非敏感设置，首次保存时记住“原文件不存在”。需要失效但数据库不可用时，在外部修改前报错；不影响保存无关选项。
4. 数据库和文件提交成功后，更新内存配置及 generation；旧 epoch 使排队的旧写入失败。直到此时才把提交视作成功。保留旧快捷键至提交完成后再注销，注销失败返回非致命告警。发事件、构造返回视图的附带失败不能伪装为“未提交”，返回已提交状态和告警。
5. 补偿失败时设置明确恢复状态，保留非敏感恢复标记，阻止翻译、连接测试和手动/自动分析发出模型请求，显示恢复错误。允许用户重新保存一致配置解除标记；现有结果仍可阅读，保留可恢复画像。不将凭据写入标记或日志。

SQLite actor 事务内只做短文件发布/恢复，不等待网络、密钥环或快捷键调用；测试必须覆盖提交失败和补偿失败。相邻内存读写通过 actor 排队，不允许旧任务在未提交期间绕过事务写入。

**替代方案：** 只把 invalidate 移到末尾，仍会在 invalidate 失败时出现“文件已改、内存未改”；先清空再快照还原会增加旧任务写回窗口。上述两种方案均不足以满足契约。通用崩溃恢复日志包含更大范围的跨资源恢复语义，本次不实现；补偿失败的非敏感恢复标记只用于显式阻止不一致请求。

### 2. 设置表单保留草稿与基线，区分本地提交与外部刷新

SettingsView 维护 `baseline`、`form`、最新外部保存配置及通知状态。dirty 比较非敏感字段，并包含临时 API Key 或删除 Key 的意图；这些敏感输入继续只在组件内。未修改表单时直接跟随更新；dirty 时保留整个草稿，显示“设置已在其他窗口更新”和“重新加载已保存设置”操作。主动重新加载丢弃草稿并清空临时 Key/删除意图，不自动合并字段。

本地保存记录提交快照，按以下规则协调事件：与本次提交一致的设置更新不作为外部冲突；成功响应以被接受的配置重建 baseline 和 form，并清除对应冲突提示；若随后已有不同配置的外部更新，保留其通知，不以迟到的本地响应静默隐藏它。失败保留非敏感草稿，沿用现有 Key 清空规则。显式保存通知后的草稿即用户选择该完整草稿作为新配置；不新增字段级合并或版本冲突协议。

**替代方案：** 无条件覆盖会丢数据；完全停止监听会让未编辑表单显示过期配置。基线加通知同时覆盖这两类情况。本次不新增离开页面拦截。

### 3. 原生 Job 拥有请求展示快照

给 Job 增加可空 `requestOptions`（`targetLanguage`、`explainTerms`），由 `run_job` 使用与模型请求相同的 config 克隆设置，在任务开始执行、显示 translating 状态前原子更新 Job 并递增 revision。后端拥有元数据，不相信模型回传值；模型 JSON Schema、Translation 内容结构和 SQLite 表保持不变。

事件与 get_job 返回完整相同对象；前端同步更新类型、fixture 和 revision 同步测试。有当前任务/结果时使用该快照渲染语言及术语提示；idle 且无结果时使用当前偏好。任务开始阶段尚无快照时不把当前设置误当成确定的结果元数据。旧结果由旧进程内存持有，升级需退出旧实例，因此不做持久化旧结果迁移。

**替代方案：** 切换设置直接清空译文会中断阅读；仅在前端记录语言会在另一窗口或恢复时失配。让 Job 拥有元数据同时覆盖请求途中修改设置与跨窗口恢复。

### 4. 用最终 ELF 和发行版依赖元数据验包

新增 `scripts/build-linux-deb.sh` 与 `scripts/verify-linux-deb.sh`，保留当前 Tauri 构建入口，在构建流程中从 release 可执行文件用 `dpkg-shlibdeps` 的发行版 symbols/shlibs 元数据求出版本依赖。若工具需要控制文件，在临时打包工作目录提供最小控制上下文；不要修改 `/var/lib/dpkg`。使用临时 Tauri 配置覆盖文件将派生依赖与 wl-clipboard、fonts-noto-cjk 合并，再打包。不得把 libc6 2.39 硬编码为所有未来产物的依赖。

验包脚本解包最终 DEB，再运行依赖推导并比较 control：依赖必须覆盖推导的最低约束，不能只核对构建前文件或仅用 ldd；用 readelf/objdump 交叉记录 GLIBC 符号下限，并检查 desktop/icon。本次现有产物的 GLIBC_2.39 是回归夹具，不是发行版普遍支持声明。若构建工具再次改变二进制，最终成品检查必须能检出依赖遗漏。缺少发行版元数据或无法解析依赖时失败，不输出“发布就绪”。

README 区分源码构建指导与预编译产物的架构、构建系统、运行库下限和实测范围；发布验收包含干净目标环境安装/启动及低版本 libc6 的拒绝解析。无法获得环境时标记未验证，不能用 `apt -s` 代替实际安装。构建脚本只产出并验证本地文件，不上传、发布或代替用户安装。

**替代方案：** 只加 `libc6 (>= 2.39)` 能处理本次符号但会在换工具链后过时；只写“Ubuntu 26.04”不能让包管理器提前阻止不兼容安装。动态依赖推导加成品验证提供持续约束。

## Risks / Trade-offs

- [SQLite、文件、凭据并非同一事务资源] → 覆盖每一失败边界及补偿失败；明确区分提交前错误和提交后告警，不声称断电原子性。
- [事务内文件写入阻塞数据库队列] → 事前完成序列化和临时文件写入，事务内只做短发布；不把网络或凭据调用放进去。
- [双窗口事件与命令返回顺序变化] → 测试事件在响应前/后及真正外部更新，复用 Job 的单调 revision 规则。
- [任务新增 IPC 字段使旧 fixture 不完整] → 后端、TypeScript 和两个窗口的测试同步调整，全量类型检查，不改变模型响应要求。
- [构建系统推导出更严格依赖] → 采用准确约束并记录范围；确需支持更旧系统时另在对应基线重建，不伪造低约束。
- [旧变更尚未同步主规格] → 本次只写独立 ADDED 要求；将来归档前检查同路径合并，不能丢失原有条款。

## Migration Plan

1. 先用临时数据和故障注入固定保存失败与两个界面缺陷，再实施修复；已有 33 项自动测试为基线。
2. 无需数据库结构迁移；新字段仅影响运行中 Job，完整退出旧实例后由同一包的前后端启动。
3. 重新构建 DEB 并验证依赖、安装和启动，记录真实完成项和被环境阻塞项。变更不自动发布新版本；版本号和发布动作由后续发布请求决定。
4. 如需回滚，先退出新实例并保留用户配置/术语数据库；遇到恢复标记不能用回滚旧版绕过，先恢复一致设置。回滚发行包仍须使用真实依赖约束。
